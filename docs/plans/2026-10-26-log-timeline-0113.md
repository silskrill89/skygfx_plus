## 5. Anomalies: bugs, impossible values, mislabelled receipts

### A. `[VehTex] matA` prints the bound pointer, not material alpha (confirmed format/vararg bug)

All 24 `[VehTex]` lines have `matA` numerically equal to `bound`:

```
[01:15:35.543] [VehTex] tex='hunter8bit128a' null=0 bound=21DBD524 env=000 spec=255 matA=568055076
   568055076 = 0x21DBD524 = bound
[01:13:41.016] [VehTex] tex='vehiclegeneric256' null=0 bound=173B5414 env=000 spec=255 matA=389764116
   389764116 = 0x173B5414 = bound
[01:20:26.627] [VehTex] tex='' null=1 bound=04C24B28 env=000 spec=255 matA=79842088
   79842088 = 0x04C24B28 = bound
```

Mechanism: `src/render/vehiclePipe.cpp:1433` uses
`tex='%s' null=%d bound=%p env=%d%d%d spec=%d matA=%u` (8 conversions) but supplies only
7 arguments (`name, null, bound, hasEnv1, hasEnv2, hasSpec, color.alpha`). `spec` consumes
alpha (255), and `matA` consumes the next stack slot, which happens to be the `bound`
pointer. This is a genuine log corruption; any future texture-alpha diagnosis is invalid.

### B. `[CoronaFeed] pool` goes negative without bound (impossible count)

```
[01:13:02.947] [CoronaFeed] pool=0 fed=0 rej(id0=64 sz=0 rgb0=0 int0=0) regFed=0
[01:13:05.023] [CoronaFeed] pool=-7 fed=0 …
[01:13:09.016] [CoronaFeed] pool=-2807 fed=0 …
[01:21:07.233] [CoronaFeed] pool=-171503 fed=0 …
```

111/111 `[CoronaFeed]` lines report `fed=0` and `rej(id0=64)` (all 64 corona slots inactive);
the `pool` value is monotonically decreasing: 0, -7, -1,297, -2,807 … -171,503. A
`NumCoronas` count cannot be negative. `src/core/main.cpp:3866` reads
`*(uint32_t*)0xC3E038` as `CCoronas::NumCoronas`; the value behaves like a pointer/time
low word, not a count. This is a wrong-address read, and it is the strongest "impossible
value" in the log. Consequence: the corona walk never feeds lights (although Forward+ is
disabled in this mode, so no visual effect here).

### C. `colorFilterEnable` mode value is silently reverted by the INI heal

At 01:12:55.922 the mode-owned value is 1; 1 ms later:

```
[01:12:55.923] [Config] colorFilterEnable=1 diverged from user intent 0 — silent write repaired (slot 0)
```

`Xbox`'s profile owns `colorFilterEnable=1` (`src/core/modeManager.cpp:251`), but the INI
user-intent latch records 0 and `cfEnableHeal()` (`src/core/main.cpp:600-605`) restores 0.
So the mode apply and the heal fight, and the effective flag is 0 despite the profile
ownership. If the Xbox profile is supposed to force the custom colour filter, this is a
functional bug, not just a log oddity. It happens once in this run because the heal is
throttled, but the value stays 0.

### D. `[PF] pf_gate` fields are skip reasons but read like enable states

```
[PF] pf_gate: mask=0x00DF5 normalBuf=1 vel=0 ssao=1 pipeChain=1 … ivGrade=1
[PostFX-REPORT] … SSAO=0 smaa=0 normalBuf=0 pipeChain=0
```

The `pf_gate` printer (`src/render/postfx.cpp:1456-1490`) sets `1` when the feature was
**skipped**, while the field names (`ssao`, `pipeChain`, `normalBuf`) read as "enabled".
E.g. the INI says `ssaoEnable=0` and `pipeChainEnable=0`, and the report says 0, yet
`pf_gate` says `ssao=1 pipeChain=1`. This is a forensic trap, not a rendering bug. It also
explains why a grep for "ssao=0" finds nothing while SSAO is actually off.

### E. `[ForwardPlus]` is absent for a legitimate but surprising reason

`forwardPlusEnable=1` in `skygfx.ini`, yet there are **0 `[ForwardPlus]` lines**. The cause
is the Xbox profile, which owns and forces the field off:

- `src/core/modeManager.cpp:293-297` (MODE_XBOX): `forwardPlusEnable=0`, `pipeChainEnable=0`,
  `normalBufferEnable=0`, `profilerEnable=0`.
- `ForwardPlus_CullAndUpload` therefore returns at `!config->forwardPlusEnable`
  (`src/render/forwardplus.cpp:1252`) after its one-time `enter` breadcrumb.

So INI users see `forwardPlusEnable = 1` and get no Forward+ in Xbox mode. That is a
policy/config-authority issue, not a missing log. The same gate explains the 0 counts for
`[PipeChain]`, `[SSAO]`, `[SMAA]`, `[Radiosity]`, `[Radiosity_VCS]`, `[Profiler]`.

### F. `[PointLights]` first-sprite receipt never fires

`[pointlights_install]` reports both call sites OK, and the code path has a one-shot
`[PointLights] base=%p count=%d` at `src/core/main.cpp:2904`. That line has **0 occurrences**
in the run despite 119 `[CoronaDraw]` sprite-flush receipts. Either the intercepted
`CSprite::RenderBufferedOneXLUSprite_Rotate_Aspect` is never called in this route, or the
hook is dead. This is the most plausible "tag should have fired but did not" candidate
worth a dedicated probe.

### G. `[BldElide]` counters are 3 orders of magnitude above visible draws

```
[01:13:05.694] [BldElide] writes skipped since last window: PS2=0 Xbox=1183 PBR=0 Sphere=0
[01:14:01.683] [BldElide] writes skipped since last window: PS2=0 Xbox=803704 PBR=0 Sphere=0
```

The counter is a per-texture-stage state-write elision counter, reported every 64 callbacks
(`src/render/buildingPipe.cpp:1106-1122`) — not a draw count. It still shows ~400k elided
writes/s while only ~250 `XboxBuilding` lines/s are logged. That is a 1,600:1 ratio,
which is plausible only if the per-object receipt is heavily throttled/sampled. Do not
use `XboxBuilding` line counts as draw counts.

### H. `ZWRITE` "forcing TRUE" does not persist across entries

```
[01:19:06.972] [BUILDING] ZWRITE off/desynced on entry (rw=0 drv=0 dev=0) — forcing TRUE for cb
[01:19:06.973] [PED] ZWRITE off/desynced on entry (rw=1 dev=0) — forcing TRUE for cb
```

47 `[BUILDING]`, 26 `[PED]`, and 17 `[VEHICLE]` entries report the same off/desynced
condition; the device-side value is 0 on every entry. If the force is meant to stick for
the callback only, fine; if it is meant to be a persistent contract, it is being undone
between callbacks. No corresponding "set FAILED" line exists, so the log cannot distinguish
these. Flag for the state-contract lane.

### I. `[PedRS] DIVERGED` contradicts the 100% clean `rs_mon_report`

- `rs_mon_report`: 44 samples, `agree=58542/58542`, `diverge=0`, `bad=0`, `sites=0`.
- `[PedRS]`: 14 `DIVERGED` out of 87 receipts, with real `blend`/`aref` device mismatches

Either the monitor samples before the ped callback (different phase) or its state set is
blind to the ped entry/exit path. This is a monitoring gap worth reconciling; the 14
divergences are real receipts, not inferred.
